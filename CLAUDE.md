# CLAUDE.md — папка `posting_vk`

В этой папке лежат **два разных проекта**. Не путать.

| Папка | Чей | Статус |
|---|---|---|
| `vkposter/` | клиентский (AlexNef), автопостинг ВК про скам-обзоры | **сдан, только чтение** |
| `my_posting/` | мой собственный, автопостинг в Одноклассники под продвижение своих услуг | активная разработка |

## Железное правило

**`vkposter/` не трогать ни при каких условиях.** Ни правок, ни коммитов, ни
переименований, ни «заодно поправлю баг». Проект сдан клиенту и работает на его
сервере. Читать оттуда код как референс — можно и нужно, писать — нельзя.

Вся работа идёт только в `my_posting/`.

# Проект `my_posting`

## Зачем он

Продвижение **своих услуг** через SEO-трафик из Яндекса на темы в группах
Одноклассников. Механика подтверждена на клиентском проекте: тема в группе ОК
(`ok.ru/group/{id}/topic/{id}`) встаёт в топ-1 Яндекса по низкочастотному запросу,
обходя специализированные сайты — за счёт траста домена `ok.ru`, собственного
`<title>` у темы и быстрой индексации.

Что продаём: **ИИ-агентов, чат-ботов и автоматизацию для бизнеса**.
Аудитория — собственники ИП и ООО, РФ, 30+ лет. Ниша не одна: автосервисы,
стройка и отделка, окна и двери, торговля, услуги — те, что реально приходят
в заказах. Агент отвечает клиентам по прайсу во всех каналах, записывает
на приём, передаёт заявки в CRM, считает по таблицам, сложное эскалирует
менеджеру.

Куда ведём трафик: **профиль на Kwork** (100+ выполненных заказов, 70+ отзывов).
Это главный актив — он закрывает основное возражение «а не пропадёт ли фрилансер
с деньгами». Задача постов не продать, а довести до профиля.

Первая группа ОК уже создана: «ИИ-агенты и чат-боты для автосервиса»,
категория «Бизнес-услуги».

## Цель — полная автоматизация

Ручного труда быть не должно. Человек участвует только в:
- пополнении списка ключевых запросов (и то по возможности автоматизировать);
- правке промпта в панели;
- разборе упавших прогонов.

Всё остальное — сбор тем, генерация, обложки, публикация, ответы в комментариях —
работает само по расписанию.

## Что меняем

### 1. Источник тем: sitemap → ключевые запросы

Главная переделка. Сейчас темы приходят из sitemap чужих сайтов. У нас чужих
сайтов нет — темы приходят из списка поисковых запросов.

Новая миграция `0023_keywords.sql`:

```sql
CREATE TABLE keywords (
  id            serial PRIMARY KEY,
  phrase        text NOT NULL UNIQUE,   -- 'ии агент для автосервиса'
  cluster       text,                   -- 'авто' / 'услуги' / 'интеграции'
  frequency     integer,                -- частотность Вордстата, если известна
  serp_weakness integer,                -- сколько UGC-страниц в топ-10
  priority      integer NOT NULL DEFAULT 0,
  status        text NOT NULL DEFAULT 'new'
                CHECK (status IN ('new','queued','used','skipped')),
  used_at       timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON keywords (status, priority DESC, id);
```

Плюс новое значение в `sources.discovery`: помимо `sitemap` и `custom` — `keywords`.
Источник с таким режимом вместо чтения карты сайта берёт очередной ключ со
`status = 'new'` и заводит `article` с `title` = фраза, `content` = null,
`content_mode` = `topic_only`. Дальше существующий конвейер
(research → generate → image → publish) работает без изменений.

**Критерий отбора ключей — не частотность, а слабость выдачи.** Ключ с
частотностью 30 и пустым топом даёт больше, чем ключ с частотностью 500 и
забитым. `serp_weakness` = сколько в топ-10 форумов, соцсетей, дзена и отзовиков.
От 3 — берём, при засилье habr/vc.ru/официальных доков — пропускаем.

Заголовок темы должен содержать **точное вхождение ключа**. Это единственное
жёсткое требование к генерации: заголовок = title страницы = то, по чему
ранжируется.

**Проверено на живой теме 26.08.2026** (`ok.ru/group/70000055464414/topic/156962062196958`).
Одноклассники собирают `<title>` страницы темы так:

```
{первая строка текста} | Интересный контент в группе {название группы} в ОК (Одноклассники)
```

Из этого три следствия, и все три жёсткие:

1. **Заголовком становится первая строка текста поста**, отдельного поля заголовка
   у темы нет. Значит ключ обязан стоять в самой первой строке — не во второй,
   не после приветствия.
2. **К заголовку приклеивается 60+ символов хвоста** с названием группы. В сниппете
   Яндекса видно около 60-70 символов, поэтому первая строка должна быть короткой:
   ключ и минимум лишнего, иначе ключевую фразу обрежет собственный хвост.
3. **`description` собирается из следующих абзацев** — первые ~200 символов после
   заголовка идут в сниппет. Начинать надо с сути, а не с раскачки.

Эмодзи-иконки в подзаголовках площадка не режет — в опубликованной теме они на месте.

**Угол подачи — защита от самосклейки.** «ии агент для автомойки» и «чат бот
для автомойки» — разные ключи, но по ним получится почти одинаковый текст.
Яндекс сочтёт их дублями и выкинет один из выдачи: мы сами себе создадим
конкурента. Поэтому у каждой формулировки свой угол, и он передаётся в промпт
параметром:

| Формулировка | Угол текста |
|---|---|
| `ии агент для {n}` | общий разбор: что умеет, как выглядит работа |
| `чат бот для {n}` | сравнение готовых конструкторов и решения под задачу |
| `сколько стоит чат бот для {n}` | цены, из чего складываются, расчёт окупаемости |
| `бот для записи клиентов в {n}` | сценарий записи, интеграция с расписанием |
| `бот для приёма заявок с авито для {n}` | интеграция с Авито и CRM, кейс |
| `автоответчик для {n}` | ночь и выходные, потерянные заявки |
| `автоматизация {n}` | шире: не только диалоги, но и отчёты, напоминания |
| `ии для обработки заявок {n}` | маршрутизация и эскалация на менеджера |

Хранить углы в `keywords.cluster` или отдельной колонкой. Плюс планировщик
не должен ставить две формулировки одной ниши подряд — разносить минимум
на неделю.

### 3. Комментарии и демо-агент — прямой OK API

postmypost комментарии не умеет в принципе, это публикатор. А демо-агент в
комментариях — **главный конверсионный инструмент проекта**, поэтому понадобится
прямой доступ к API Одноклассников.

Механика: под темой стоит приписка «в комментариях отвечает тот самый агент,
спросите его что-нибудь». Человек пишет вопрос → отвечает наш же агент по прайсу
→ сложный вопрос эскалируется в Telegram владельцу. Продукт демонстрирует себя
в самой конверсионной точке, а «передаю менеджеру» = горячий лид.

Что нужно:
- приложение в ОК, права на работу с группой, `access_token`;
- новый `src/lib/ok.js` — структуру брать с `postmypost.js` (там правильно
  сделаны ретраи, фатальные статусы, обработка ошибок);
- новый `src/services/comment-agent.js` — поллинг новых комментариев по темам,
  ответ через OpenRouter с контекстом прайса, эскалация в Telegram;
- отдельный cron, не смешивать с постингом.

Публикацию при этом можно оставить на postmypost — два канала сосуществуют
нормально. Переезжать на OK API целиком имеет смысл, только если postmypost
начнёт мешать или ради экономии на тарифе.

### 4. Промпт

Клиентский промпт (`docs/prompts/post_prompt.seed.txt`) выбросить целиком —
он про «отзывы на мошенников» и нам не подходит ничем.

Новый промпт пишет **экспертный пост под ключевой запрос**. Требования:

- заголовок с точным вхождением ключа, без кликбейта;
- 1500–2500 знаков;
- структура: проблема бизнеса → как решает агент → пример диалога с клиентом →
  что нужно для внедрения;
- **обязательно пример реального диалога** — это лучше любого описания
  показывает продукт;
- живой язык, без канцелярита и без «в современном мире»;
- эмодзи-иконки в подзаголовках — как в клиентском промпте, для ОК это работает.

Рекламный блок в конце (вместо клиентского `proverka-zarabotka.online`):

```
--------
Делаю таких агентов на заказ. На Kwork 100+ выполненных проектов
и 76 отзывов, из них 75 положительных — видно, что и кому делал:
{ССЫЛКА_ЧЕРЕЗ_РЕДИРЕКТОР}

Покажу демо на вашем прайсе до оплаты.
--------
```

Два элемента: цифры снимают страх работы с фрилансером, «демо до оплаты» снимает
риск. Про ответы в комментариях не писать — OK API отменён, отвечать там некому.

**Ссылка не в каждый пост.** Клиентская система ставит рекламный блок в 100%
постов — у нас так нельзя: одинаковый коммерческий блок в каждой теме быстрее
ловит урезание охвата в ОК и подозрение на спам у Яндекса. Ставить в каждый
второй-третий, в остальных — «контакты в описании группы». Сделать настройкой
в панели (`ad_block_every_n`).

### 5. Редиректор: учёт переходов по ссылкам

Прямые ссылки на Kwork не ставить. Kwork не отдаёт источник трафика, Метрику
туда не поставить — без своего редиректора мы не узнаем, какая тема и какой
ключ приносят переходы, и масштабировать будет нечего.

Схема: в посте стоит `https://{DOMAIN}/k/{post_id}` → наш роут пишет факт
перехода в БД и отправляет человека на профиль Kwork.

**Миграция `0027_clicks.sql`:**

```sql
CREATE TABLE clicks (
  id          bigserial PRIMARY KEY,
  post_id     bigint REFERENCES posts (id) ON DELETE SET NULL,
  group_id    integer REFERENCES groups (id) ON DELETE SET NULL,
  keyword_id  integer REFERENCES keywords (id) ON DELETE SET NULL,
  target      text NOT NULL,          -- 'kwork' | 'tg' | 'max'
  visitor     text,                   -- sha256(ip + user_agent + соль), не сырой IP
  user_agent  text,
  referer     text,                   -- откуда пришёл: ok.ru, поиск, прямой заход
  is_bot      boolean NOT NULL DEFAULT false,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON clicks (post_id, created_at);
CREATE INDEX ON clicks (created_at) WHERE is_bot = false;
```

**Пять вещей, которые ломают учёт, если о них не знать:**

1. **Редирект только `302`, никогда `301`.** Постоянный редирект браузер кеширует
   намертво: второй и все последующие переходы того же человека до сервера
   не долетят вообще. Статистика тихо занизится в разы, и понять это по цифрам
   невозможно.
2. **Отсекать ботов.** По ссылке пойдут поисковые роботы и превьюшный робот ОК
   (он дёргает ссылку при публикации поста, чтобы построить сниппет). Без
   фильтра каждый пост получит «переход» в момент публикации, и вся картина
   будет ложной. Фильтровать по `user_agent` (`bot`, `crawler`, `spider`,
   `yandex`, `google`, `preview`), писать в БД с `is_bot = true`, а не выбрасывать —
   пригодится, чтобы понять, что именно отсеклось.
3. **Дедуп по посетителю.** Один человек кликнул трижды — это один переход.
   Считать уникальные `visitor` в окне 24 часа. Хранить хеш, не сырой IP.
4. **Ссылку в текст подставляет код, а не ИИ.** В промпте стоит плейсхолдер
   `{ССЫЛКА}`, модель его не трогает. Проблема в порядке: `post_id` известен
   только после вставки в `posts`, а ссылка нужна внутри `body`. Решение —
   сохранить пост, получить id, вторым запросом заменить плейсхолдер, и только
   потом публиковать. Не наоборот: опубликованный пост с `{ССЫЛКА}` в тексте
   не отредактировать задним числом.
5. **Ссылка не в каждом посте** (см. `ad_block_every_n` в разделе 4). Значит
   у части постов переходов не будет по определению — при анализе делить на
   число постов *со ссылкой*, а не на все.

**Что ещё вешается на редиректор:** короткие ссылки на Telegram и MAX для
автоответов группы (`/k/tg`, `/k/max`). Ссылка MAX длиной за сто символов в
каждом автоответе раздувает текст и выглядит подозрительно, а так — заодно
посчитаем, какой канал связи люди выбирают.

**Отчёт в панели** — отдельная страница: переходы по темам, по ключам, по
кластерам, за период, только не-боты, уникальные. Это главный экран проекта:
по нему принимается решение, какие кластеры ключей масштабировать, а какие
закрывать.

**Ограничение, которое надо принять сразу.** Цепочка обрывается на Kwork:
дальше переход → заказ мы технически не отследим, Kwork такой статистики не даёт.
Закрывается только вопросом «откуда вы про меня узнали?» при первом контакте,
и его стоит задавать всегда — в том числе устами комментарий-агента.
Косвенно поможет корреляция по времени, но на малых числах это гадание.

## Откуда брать ключевые запросы

По убыванию ценности:

1. **Свои 100+ выполненных заказов на Kwork.** Лучший источник, и он есть только
   у нас. Каждый заказ — задача, которую кто-то формулировал своими словами и за
   которую заплатил: спрос подтверждён деньгами, а не догадкой. Из каждого —
   тема с настоящим кейсом внутри.
2. **Комбинаторика ниша × формулировка.** Без всякого API:
   `20 ниш` (автосервис, СТО, автосалон, автомойка, шиномонтаж, магазин запчастей,
   стоматология, салон красоты, клиника, доставка…) × `8 формулировок`
   (`ии агент для X`, `чат бот для X`, `автоответчик для X`, `бот для записи
   клиентов в X`, `автоматизация X`, `сколько стоит чат бот для X`, …) = 160 тем,
   пять месяцев постинга.
3. **Подсказки Яндекса** — `suggest.yandex.ru/suggest-ya.cgi?srv=serp&part={q}`,
   бесплатно, без ключа. Рекурсивно с добавлением букв а-я. Эндпоинт неофициальный,

## Грабли окружения (проверены на клиентском проекте, не переоткрывать)

- **Автосборка в dev — только `nodemon --legacy-watch`** (polling). Нативный
  `node --watch` правки хостовых файлов через bind-mount Docker Desktop на
  Windows не видит: inotify не пробрасывается.
- **`tzdata` в образе обязательна.** Без пакета `TZ` на alpine игнорируется и
  контейнер живёт в UTC. Нужна МСК: `post_at` идёт с `+03:00`, расписание
  задаётся в часах.
- **Значения окружения читаются через `trim`** (`src/config.js`). `.env`,
  отредактированный на Windows, приходит с CRLF, значение получает хвостовой
  `\r`: пароль перестаёт совпадать, API-ключ даёт загадочный 401.
- **Новую переменную окружения надо добавить и в `docker-compose.yml`** — там
  переменные перечислены явно, наличия в `.env` недостаточно.
- **Правка уже применённой миграции падает по контрольной сумме** — это защита,
  а не баг. Нужна новая миграция.
- **`POST /publications` в postmypost не ретраится** — повтор после фактически
  созданной публикации даёт дубль на стене.
- **Ответ postmypost всегда JSON-массив**, даже на одиночный объект: `[{...}]`.
- **`translateTime` в pino-pretty без префикса `SYS:` печатает UTC.** Контейнер
  живёт в МСК, а лог показывает время на три часа раньше — расхождение с `post_at`
  и расписанием ищется долго. Правильно: `'SYS:dd.mm.yyyy HH:MM:ss'`.
- **`fetch` из контейнера падает с «fetch failed» там, где `wget` отвечает 200.**
  Причина не в маршруте (это была неверная догадка, прожившая до 27.08.2026),
  а в «happy eyeballs» Node: он пробует IPv6 и IPv4 параллельно и даёт каждой
  попытке 250 мс. IPv6-маршрута у контейнера нет, а рукопожатие по IPv4 до
  Cloudflare (openrouter.ai, api.kie.ai) с российского канала занимает секунду
  и дольше — не укладывается. Лечится строкой
  `net.setDefaultAutoSelectFamilyAttemptTimeout(5000)` в `src/lib/http-client.js`.
  Сборка образа отдельно лечится зеркалом `NPM_REGISTRY` в `.env`
  (`https://registry.npmmirror.com`) — там свой резолвер, не Node.
- **На общем сервере прод — отдельный compose-файл, а не слой поверх базового.**
  `docker compose -f base -f prod` сервисы ОБЪЕДИНЯЕТ, а не заменяет: свой
  `postgres` из базового файла поднимется всё равно, а свой `caddy` займёт 80 и 443
  и уронит соседей по серверу. Плюс `okhost rebuild` вызывает голый `docker compose`
  без флагов — какой файл считать рабочим, задаётся строкой `COMPOSE_FILE`
  в серверном `.env`.
- **`sed -i` по файлу, смонтированному в контейнер, до контейнера не доезжает.**
  Bind-mount одного файла держит инод, а `sed -i` пишет новый файл на то же имя.
  Контейнер продолжает видеть старое содержимое сколько угодно долго. Правильно —
  `cat /tmp/новый > файл` (инод сохраняется) или перезапуск контейнера.
- **`provider: { require_parameters: true }` в OpenRouter отсекает всех, кроме
  Google.** Он ставится вместе со строгой JSON-схемой и требует от провайдера
  поддержки structured outputs; Anthropic и OpenAI её не заявляют, и запрос
  отвечает `404 No endpoints found`. Выглядит как «модель недоступна», хотя
  недоступно сочетание. Поэтому текст поста берётся обычным текстом, без схемы.

## Ключевое архитектурное решение: факт-база вместо кейсов

**Кейс под каждый ключ не пишем.** Это ручной труд, который не масштабируется на
600 тем в месяц. Вместо этого фактура добывается **один раз** и дальше
рекомбинируется машиной.

Источники фактуры:
- `~/.claude/projects/C--Users-GigaChat-Downloads-claude-*/*.jsonl` — 43 клиентские
  переписки. **Сами папки в `Downloads\claude` пустые**, это рабочие каталоги;
  переписка лежит только в `.jsonl`;
- `D:\claude\orders` (~19 МБ) и `Downloads\ЗАКАЗЫ` (24 проекта);
- `отзывы.txt` в корне — 76 отзывов, 75 положительных, 1 отрицательный.
  Цифру «75 из 76» ставить в текст: она сильнее круглого «70+» и проверяется кликом.

Типы карточек в БД: **задачи** (боль словами клиента), **грабли** (API Авито за
отдельные деньги, вложения не проходят через штатный коннектор amoCRM, чужие группы
ОК не парсятся, тарифы Wazzup и postmypost), **цены** (реальные вилки и ежемесячные
расходы), **возражения**, **цитаты отзывов**.

Пост собирается по рецепту: ключ задаёт заголовок, нишу и угол; начинка берётся
из базы — одна карточка задачи, одна-две грабли, вилка цены, возражение, иногда
цитата отзыва, плюс сгенерированный под нишу пример диалога (это ~40% объёма
и он уникален всегда).

**Обезличивание жёстко в коде.** Ни ников, ни брендов, ни ссылок на аккаунты
клиентов. «Компания, которая пригоняет авто под заказ» вместо конкретного названия.
Иначе первый же клиент, нашедший себя в поиске, — проблема, а не актив.

**Анти-дубль двумя механизмами:** счётчик использований у каждой карточки (факт не
чаще раза в N постов, два поста подряд не берут одну карточку) и шингловая проверка
схожести с уже опубликованным перед отправкой. Превысил порог — пересобираем
с другим набором фактов. Тексты расходятся не стилем, а **разными фактами внутри**.

## Что добавилось в кластеры ключей

Разбор 43 переписок показал три кластера, которых в первоначальном плане не было:

1. **Расчёты по своим таблицам** — 6 обращений из 43, самый повторяющийся денежный
   запрос: смета, КП, расчёт стоимости по Excel клиента.
2. **Работа в условиях РФ** — оплата зарубежных сервисов, доступ, аналоги, 152-ФЗ,
   закрывающие документы. Специфично для ИП/ООО, выдача устаревшая.
3. **Внутренняя рутина** — 5 обращений: входящая почта, сроки по договорам,
   дебиторка, протоколы, версии документов, распознавание сканов.

Плюс правило словаря: к каждой технической формулировке заводить **бытовую пару**.
Собственник 40 лет ищет не «ии агент для автосервиса», а «программа для записи
клиентов в автосервис», не «эскалация лидов», а «менеджер не успевает отвечать
на заявки». Бытовая половина почти всегда со слабее забитой выдачей.

## Критерий эксперимента

Это эксперимент, у него есть точка выхода: **4 недели, 60–80 тем, три цифры** —
сколько в индексе, сколько в топ-10 по своему ключу, сколько переходов
по редиректору. Меньше половины в индексе или ноль переходов — механика на нашей
тематике не работает, закрываем. Десяток тем в топе и переходы идут —
масштабируем группами.

# Старт сессии (обязательно)

Проект ведётся по методологии `/okplan`. Прогресс лежит в трёх слоях, и при
расхождении верить нижнему: **git-тег > чекбоксы в ROADMAP > проза STATUS**.

1. Прочитать `docs/STATUS.md` — текущий этап, активная работа, блокеры.
2. `git tag -l "stage-*"` — сверить с колонкой «Закрывающий тег». Тег, которого
   нет в таблице, означает, что STATUS устарел: сначала чиним STATUS.
3. `git log --oneline -10` — что менялось последним.
4. Открыть `docs/07_ROADMAP.md` на текущем этапе — там открытые чекбоксы.

Этап закрывает **человек**, не Claude: критерии проверяются вживую, результат
проверки с конкретикой пишется в «Историю закрытий», и только после этого
ставится тег.

**В конце этапа — короткий список критериев приёмки**, 3-6 пунктов: что открыть,
что нажать, что должно получиться. Только то, по чему видно, работает этап или
нет. Переименования, комментарии, чистку текстов в этот список не тащить —
им место в коммите и в «Истории закрытий», а не в списке на проверку.

Нумерация миграций: `0022_ok_channel` (этап 1), `0023_keywords` (этап 2),
`0024_facts` (этап 3), `0025_post_facts` (этап 4), `0026_image_prompt` (этап 5) —
все применены. Редиректор из этапа 6 получит следующий свободный номер,
`0027_clicks`: каждая новая миграция сдвигает план, а редактировать применённую
нельзя — падает по контрольной сумме.
