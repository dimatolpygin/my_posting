# Дорожная карта реализации my-posting

Девять этапов от копии конвейера до решения «масштабируем или закрываем».
Каждый этап заканчивается **демонстрируемым результатом** — тем, что можно
потрогать руками, а не «переписал слой X».

Ключевая идея: конвейер уже обкатан в проде на клиентском проекте, поэтому
этап 0 — это сразу живая вертикаль, а не каркас. Дальше меняются только вход
(ключи вместо карты сайта), выход (ОК вместо ВК) и начинка текста (факт-база).

> **Где смотреть прогресс**: текущий статус всех этапов — в [`STATUS.md`](STATUS.md).
> Внутри каждого этапа ниже — чекбоксы конкретных acceptance-пунктов. Закрытие
> этапа сопровождается git-тегом `stage-N-done`.

| # | Этап | Главный артефакт | Зависит от |
|---|---|---|---|
| 0 | Каркас my-posting | система стартует локально под своим именем, панель открывается | — |
| 1 | Канал: ВК → Одноклассники | тема, опубликованная системой в группу ОК | 0 |
| 2 | Ключи как источник тем | прогон берёт фразу из `keywords` и заводит по ней статью | 0 |
| 3 | Факт-база | обезличенные карточки фактов в БД, видны и правятся в панели | 0 |
| 4 | Промпт и сборка поста из фактов | пять текстов, которые не стыдно опубликовать | 2, 3 |
| 5 | Первые публикации потоком | десять тем в группе за сутки, все с обложками | 1, 4 |
| 6 | Редиректор и учёт переходов | страница отчёта: переходы по темам, ключам, кластерам | 5 |
| 7 | Деплой на okhost | работает без ноутбука, выкат по пушу в master | 6 |
| 8 | Наблюдение и решение | три цифры и вердикт по эксперименту | 7 |

## Этап 0 — Каркас my-posting

**Цель**: клиентский конвейер живёт под своим именем, в своём репозитории,
и поднимается локально одной командой.

**Что делаем**:
- копия `vkposter/delivery` в корень `my_posting` (без чужой git-истории,
  секретов и `node_modules`);
- переименование: `package.json` → `my-posting`, `POSTGRES_USER`/`POSTGRES_DB`
  → `myposting`, дефолты в workflow деплоя;
- свой репозиторий, ветка `dev`, `dostupi_my.txt` в `.gitignore`;
- `docs/STATUS.md` и `docs/07_ROADMAP.md`, ритуал старта сессии в `CLAUDE.md`;
- локальный запуск и прогон миграций.

**Критерии приёмки** (закрытие → tag `stage-0-done`):
- [x] `docker compose up -d` поднимает `postgres` и `app`, оба healthy
- [x] `curl http://localhost:3000/health` отвечает 200
- [x] Миграции `0001`–`0021` применены, таблицы `sources`, `articles`, `posts`,
      `groups`, `prompts` существуют
- [x] Панель на `http://localhost:3000` пускает по `ADMIN_LOGIN`/`ADMIN_PASSWORD`
      и показывает пустые списки без ошибок
- [x] В логах контейнера русский `pino-pretty`, время московское
- [x] `git log` в `my_posting` — только свои коммиты, ветка `dev`
- [x] `git status` не показывает `dostupi_my.txt`

## Этап 1 — Канал: ВК → Одноклассники

**Цель**: система публикует в группу Одноклассников, а не на стену ВК.

**Что делаем**:
- канал выносится в настройку (`pmp_chanel_id`, дефолт `5`), а не хардкодится;
- `vkAccounts()` → `okAccounts(chanelId)`, фильтр по каналу из настройки;
- `vkUrlFrom()` → `okUrlFrom()`: ищет адрес темы `ok.ru/group/{id}/topic/{id}`;
- миграция `0022_ok_channel.sql`: настройка канала, `publications.vk_url` →
  `post_url`, комментарии к колонкам вместо неправды про «id со знаком минус»;
- `sync-groups` подтягивает подключённые аккаунты ОК;
- заглушки postmypost в `/_debug` отдают ОК-аккаунты с положительными id;
- ручная публикация одной темы через панель.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [x] `GET /accounts` через код возвращает аккаунт `2239557`, канал `5`,
      `external_id` `70000055464414`
- [x] Группа появилась в панели после `sync-groups`, `connection_status` = 1
- [x] Тестовая тема, отправленная из панели, реально видна в
      `ok.ru/group/70000055464414`
- [x] У опубликованной темы есть обложка (картинка дошла через `PUBLIC_BASE_URL`)
- [x] Кнопка «Найти ссылку» вернула адрес вида `ok.ru/group/.../topic/...`,
      и он сохранён в `publications.post_url`
- [x] В панели и логах нигде не осталось «ВК»: ссылки ведут на `ok.ru`,
      подписи говорят про темы, а не про стену
- [x] В коде не осталось `chanel_id = 2` и утверждений про «id со знаком минус».
      Исключение — применённые миграции `0002` и `0010`: их правка падает
      по контрольной сумме, поэтому истина дописана `COMMENT ON COLUMN` в `0022`

## Этап 2 — Ключи как источник тем

**Цель**: на входе конвейера — поисковая фраза, а не карта чужого сайта.

**Что делаем**:
- миграция `0023_keywords.sql`: `phrase`, `cluster`, `angle`, `frequency`,
  `serp_weakness`, `priority`, `status`;
- новое значение `sources.discovery = 'keywords'`;
- той же миграцией гасятся клиентские источники, засеянные в `0002`/`0003`
  (`scama.net`, `all-comment` и остальные), и `ad_link` меняется со ссылки
  клиента на свой редиректор;
- заливка ста фраз из `темы.txt` с углами подачи;
- раздел ключей в панели: список, статусы, добавление руками;
- правило разноса: два ключа одного кластера не идут подряд.

**Критерии приёмки** (закрытие → tag `stage-2-done`):
- [x] Миграция применена, в `keywords` сто строк, у каждой есть `cluster` и `angle`
- [x] Клиентских источников в `sources` не осталось: `SELECT` по `scama`,
      `all-comment` пусто; `ad_link` указывает на свой редиректор
- [x] Прогон источника с `discovery = 'keywords'` создаёт `article`
      с `title` = фраза, `content` = null, `content_mode` = `topic_only`
- [x] Взятый ключ переходит в `status = 'used'` и повторно не берётся
- [x] В панели видно список ключей со статусами, фраза добавляется руками
- [x] Два подряд запланированных поста — из разных кластеров

## Этап 3 — Факт-база

**Цель**: фактура добыта один раз и лежит в БД карточками, готовая к рекомбинации.

**Что делаем**:
- миграция `0024_facts.sql`: тип (`задача`/`грабли`/`цена`/`возражение`/`цитата`),
  текст, ниша, канал, счётчик использований, дата последнего использования, флаг
  активности;
- разбор `отзывы.txt`, папок заказов и клиентских переписок в карточки;
- обезличивание в коде: ни ников, ни брендов, ни ссылок на аккаунты клиентов;
- раздел фактов в панели.

**Критерии приёмки** (закрытие → tag `stage-3-done`):
- [x] Миграция применена, в `facts` не меньше 60 карточек, все пять типов
      представлены
- [x] Проверка регулярными выражениями (латинские ники, `@`, `http`, названия
      брендов из списка) не находит ничего; двадцать случайных карточек прочитаны
      глазами
- [x] В панели карточки видно, можно править, выключать и заводить новые
- [x] У каждой карточки виден счётчик использований

## Этап 4 — Промпт и сборка поста из фактов

**Цель**: пять текстов подряд, которые не стыдно опубликовать, собранные машиной.

**Что делаем**:
- клиентский промпт про «отзывы на мошенников» выбрасывается целиком;
- новый промпт: ключ задаёт заголовок, нишу и угол, начинка приходит
  параметрами из факт-базы;
- рецепт сборки: задача + одна-две грабли + вилка цены + возражение,
  иногда цитата отзыва, плюс сгенерированный пример диалога;
- анти-дубль: счётчик использований карточек и шингловая проверка схожести
  с уже опубликованным;
- `ad_block_every_n` и подстановка реф-ссылок кодом по плейсхолдерам.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [x] Промпт лежит в БД, правится в панели, версии сохраняются
- [x] У всех пяти сгенерированных постов заголовок содержит **точное вхождение**
      фразы ключа
- [x] Длина каждого — 1500–2500 знаков, внутри есть пример диалога с клиентом
- [x] Два поста по соседним ключам одной ниши расходятся: шингловая схожесть
      ниже порога
- [x] Использованные карточки помечены, одна карточка не попадает в два поста подряд
- [x] Рекламный блок стоит не в каждом посте, реф-ссылка — не больше одной
      и только там, где тема про это
- [x] В тексте нет тире-артефактов и markdown-разметки (постобработка отработала)

## Этап 5 — Первые публикации потоком

**Цель**: система сама, по расписанию, наполняет группу.

**Что делаем**:
- квота `posts_per_day` на группу, слоты и джиттер;
- обложки на каждую тему;
- разбор упавших прогонов в панели.

**Критерии приёмки** (закрытие → tag `stage-5-done`):
- [ ] За сутки в группе появилось десять тем, поставленных планировщиком
- [ ] У каждой темы своя обложка
- [ ] Ни одного дубля публикации
- [ ] Упавшие прогоны видны в панели с причиной, а не молча теряются
- [ ] Заголовки десяти тем — десять разных ключей, без повторов темы

## Этап 6 — Редиректор и учёт переходов

**Цель**: видно, какая тема и какой ключ приносят переходы.

**Что делаем**:
- миграция `0025_clicks.sql`;
- роут `/k/{post_id}` → `302` на профиль Kwork, плюс `/k/tg`, `/k/max`,
  `/k/visa`, `/k/vps`;
- отсев ботов по `user_agent` с записью `is_bot = true`;
- дедуп по хешу посетителя в окне 24 часа;
- подстановка ссылки в текст **после** сохранения поста, до публикации;
- страница отчёта.

**Критерии приёмки** (закрытие → tag `stage-6-done`):
- [ ] `/k/{post_id}` отвечает именно `302` (не `301`) и ведёт на профиль Kwork
- [ ] Переход записан в `clicks` с `post_id`, `keyword_id`, `referer`
- [ ] Запрос с `user_agent`, содержащим `bot`, пишется с `is_bot = true`
      и в отчёт не попадает
- [ ] Три перехода одного посетителя за час дают одну уникальную запись в отчёте
- [ ] В опубликованном тексте нет плейсхолдера `{ССЫЛКА}` — стоит рабочий адрес
- [ ] Страница отчёта показывает переходы по темам, ключам и кластерам за период,
      цифры сходятся с прямым SQL

## Этап 8 — Наблюдение и решение

**Цель**: эксперимент закрыт цифрами, а не ощущениями.

**Что делаем**:
- четыре недели, 60–80 тем;
- снимаем три цифры: сколько в индексе, сколько в топ-10 по своему ключу,
  сколько переходов по редиректору;
- решение: масштабировать группами или закрывать.

**Критерии приёмки** (закрытие → tag `stage-8-done`):
- [ ] Опубликовано не меньше 60 тем
- [ ] Снята индексация по всем темам, цифра записана
- [ ] Снята позиция по каждому ключу, цифра записана
- [ ] Переходы за период выгружены из отчёта
- [ ] Вердикт по эксперименту записан в «Историю закрытий» STATUS
